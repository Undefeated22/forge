# ENTERPRISE PRODUCTION READINESS AUDIT SOP (v14.0)

## OPERATIONAL PRINCIPLES & GUARDRAILS
- **Zero Theatricality:** Evaluate against realistic production loads. Do not manufacture crises.
- **Evidence-Based Grounding:** Every finding must anchor to a specific file or traceable import. **If evidence quality is "Insufficient", do not elevate it into a finding. Record it under "Cannot Review & Limitations".**
- **Hypothesis-Driven:** Treat categories as hypotheses to evaluate, not defects to confirm.
- **Confidence vs. Severity:** Severity reflects production impact. Confidence reflects the strength of evidence. Evaluate independently.
- **Intentional Complexity vs. DRY:** Consolidate code only when it demonstrably improves maintainability without coupling unrelated domains.
- **Cryptographic No-Fly Zone:** You may *read* cryptographic modules to verify integrations, but are **strictly forbidden** from writing modifications to these files.
- **No Filler:** Keep findings concise. Prioritize evidence and remediation over background explanations.

## EXECUTION MODES
Determine execution mode before beginning. If unspecified, default to **Autonomous Mode**.
- **Interactive Mode:** Pause and wait for user confirmation after every Phase checkpoint.
- **Autonomous Mode:** Proceed through all Phases automatically and output the final report.

---

## PHASE 0: BOOTSTRAP, INVENTORY & ADAPTIVE SCALE
**Objective:** Establish operational capabilities and scope.
1. **Capability Bootstrap:** Determine available tools (shell, git, compilers, tests, CI/Docker). Adapt your strategy.
2. **Adaptive Complexity:** Estimate complexity based on file count, module count, and dependency density.
3. **Ecosystem & Scope:** Detect primary languages, frameworks, and architecture. Adapt terminology to the detected stack.
4. **Baseline Health:** Search for build errors, failing tests, and tech debt markers (`TODO`, `FIXME`, `HACK`, `panic`).

---

## PHASE 1: TOPOLOGY & DETERMINISTIC INVESTIGATION
**Objective:** Profile topology and audit components in strict risk-based order.
1. **Import Graph Analysis:** Trace cross-file imports for circular dependencies, boundary bleeding, and hotspots.
2. **Deterministic Investigation Order:** Audit strictly in this order (skip if inapplicable):
   1. Authentication & Authorization
   2. Secrets & Key Management
   3. Configuration & Environment
   4. Persistence & Data Access
   5. External APIs & Webhooks
   6. Queues, Async Workers & Caching Layers
   7. Core Business Logic
   8. Utilities & Shared Libs
   9. Tests

---

## PHASE 2: CONTRACT VERIFICATION & SUPPLY-CHAIN AUDIT
**Objective:** Inspect the operational perimeter and dependency footprint.
1. **API Contract Drift:** (If applicable) Compare specs/generated contracts against actual implementation.
2. **Supply Chain Scans:** Use locally available metadata to identify deprecated, duplicate, or unmaintained dependencies.

---

## PHASE 3: EXECUTION, OPERATIONAL READINESS & COST ENGINEERING
**Objective:** Investigate active data flows, operability, and resource economics.
1. **Performance Profiling:** Categorize as statically proven, strongly suggested, configuration-dependent, or requiring profiling.
2. **Operational Readiness:** Review graceful shutdown, health endpoints, feature flags, and rollback safety.
3. **Cost Engineering:** Identify patterns likely to increase infrastructure cost (e.g., redundant API calls, excessive DB trips).
4. **Distributed Systems:** Evaluate for missing idempotency keys, race conditions, distributed locking defects, or cache invalidation flaws.

---

## PHASE 4: FINAL REPORT GENERATION

Before producing the report, ensure it contains no duplicate findings, unsupported conclusions, or inconsistent severity assignments. Order all findings strictly by: **Severity $\to$ Blast Radius $\to$ Confidence $\to$ Ease of Remediation.**

Generate the final report using strictly the following structure:

### 1. AUDIT METADATA
- **Audit Date:** [Date] | **Commit/Branch:** [Hash / Name]
- **Execution Mode:** [Interactive / Autonomous]
- **Capabilities Used / Missing:** [List tools]
- **Files Analyzed:** [Estimated count read vs. skipped]

### 2. REVIEW COMPLETION CHECKLIST
- Authentication: [Reviewed / Not Applicable / Unable to Review]
- Authorization: [Reviewed / Not Applicable / Unable to Review]
- Configuration: [Reviewed / Not Applicable / Unable to Review]
- Persistence: [Reviewed / Not Applicable / Unable to Review]
- Tests: [Reviewed / Not Applicable / Unable to Review]
- Infrastructure/CI: [Reviewed / Not Applicable / Unable to Review]
- Secrets Management: [Reviewed / Not Applicable / Unable to Review]
- External APIs: [Reviewed / Not Applicable / Unable to Review]

### 3. CANNOT REVIEW & LIMITATIONS
Explicitly list what could not be inspected (including "Insufficient Evidence" hypotheses).
- **Unable to review:** [Component/System] | **Because:** [Reason] | **Impact on confidence:** [High/Medium/Low]

### 4. ARCHITECTURAL DRIFT
- **Current Architecture:** (What the system was designed to be, based on ADRs or framework defaults).
- **Expected Architecture:** (Based strictly on the repository's documented architecture or the dominant pattern actually implemented. Do not assume industry-standard architectures without evidence).
- **Observed Drift:** (How the actual implementation deviates).
- **Business Impact:** (Cost, velocity, or reliability impact).

### 5. VERIFIED ARCHITECTURAL STRENGTHS
Only include strengths supported by direct evidence (e.g., "Proper singleton lifecycle", "Consistent validation boundaries").

### 6. REQUIRED FINDINGS FORMAT

- **Target Architecture Solution:** (Pragmatic pattern to resolve the issue).

**Release Decision:**
*Absolute Blockers:* Confirmed authentication/authorization bypass, secret/credential exposure, data corruption risk, remote code execution (RCE), or exploitable injection affecting production data instantly forces a "Red" decision.
- 🟢 **Green (Production Ready):** Zero P0/P1 issues, no blockers.
- 🟡 **Yellow (Ready After Minor Fixes):** Zero P0 issues, no blockers.
- 🟠 **Orange (Major Refactoring Required):** Unresolved P0 issues, or any blocker.
- 🔴 **Red (Not Production Ready):** Critical absolute blockers present.

### 9. ACTIONABLE REFACTOR ROADMAP
Organize fixes into an execution plan. For each item, list: **Dependencies, Parallelizable, Recommended Owner, and Estimated Duration.**
- **Sprint 1 (Critical Path):** P0s and security blockers.
- **Sprint 2 (Debt & Scale):** P1s and high-ROI architectural changes.
- **Sprint 3 (Hygiene):** P2s, P3s, and parallelizable work.

*(Note: Implementation and code modifications are out of scope for this audit and must be handled via a separate protocol.)*
